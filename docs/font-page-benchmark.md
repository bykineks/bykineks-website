# BYKINEKS adaptive font-page benchmark

## Purpose

Bia establishes a quality baseline, not a mandatory page template. Share visual discipline, accuracy and interaction conventions; choose the page's main experience from the target font's actual strength and visitor task. Never copy Bia's specifications, category arrays, axis controls, examples, feature exclusions or style counts into another font page.

## Starting a request

For “sekarang kita beresin font X”, resolve its actual page/assets and read its profile. Inspect latest repository state and the live page when available. Preserve any narrower user scope. State the font's distinguishing strength and the proposed bounded scope in a short update; then perform the requested audit or revision without asking the user to repeat known context. If the request is broad, start with the target page's existing section map and capability audit before bounded implementation. Do not infer permission to redesign other pages or publish.

Choose an appropriate branch from current main while preserving local work. Track evidence, hypothesis and unresolved questions separately. Existing marketing copy is evidence of a claim, not verification of a font capability.

## Build the capability profile first

Record source paths and verification date/commit for:

- Product name, role/use cases, distinguishing strength and visitor tasks.
- Actual static/variable font files and which assets the page loads.
- Style inventory from fonts or authoritative product inventory; named instances alone do not establish package contents.
- Internal glyph count, counting convention, Unicode mappings, displayed entry count, duplicates and missing preview coverage. Alternate glyphs and ligature sequences are not interchangeable with Unicode character counts.
- Variable axis tags, names, bounds and named-instance coordinates. Use no synthetic skew/bold to impersonate an actual style.
- GSUB/GPOS features, affected characters/sequences, language/script conditions and conflicts. Feature tags do not universally imply the same visual effect across families.
- Script coverage from cmap plus shaping and representative-text checks; a language-name list alone does not prove linguistic support.
- Existing licensing and download destinations; preserve real specifications and links, with no invented prices or licensing promises.

Update only the target profile with verified findings. Unknown fields stay unknown until checked. Preserve approved product naming conventions where internal font naming differs, documenting the distinction.

## Choose modules by relevance

| Capability or visitor need | Appropriate experience | Skip or adapt when |
| --- | --- | --- |
| Several meaningful design axes/families | Compare voices, real axis controls, presets | Static or single-style fonts do not get fake axes or arbitrary voice cards |
| Extensive OpenType system | Feature-led specimen, before/after examples, compatible groups | Features are absent or do not visibly affect the sample |
| Interlock/ligature composition | Pair/word builder, verified joins and set comparison | Do not present arbitrary pairs as supported joins |
| Multiscript system | Script switcher, native text, shaping/diacritics and mixed-script comparisons | Do not reuse Latin-centric categories or claim unverified languages |
| Symbols/pictograms | Category finder, outline study, Unicode/name search, functional compositions | Paragraph, case and wordmark presets may be irrelevant |
| Text/interface typography | Reading or information-density samples, hierarchy and numerals | Large decorative headlines alone do not demonstrate the intended use |
| Small static family | Focused style selector and application examples | Fewer meaningful tools are better than inactive controls |

Retain useful existing sections. Clearly distinguish existing structure from proposed modules. Reorder only for a concrete target-page reason. Keep advanced controls secondary; the first useful action should be obvious without font-engine knowledge. Use actual text rendered with the font when it communicates the design better than an image. Label invented application studies as concepts, never client work.

## Shared quality contract

- Typography, spacing, rules, palette, grid, focus states and terminology remain consistent across pages.
- Custom text survives style/voice changes. Destructive preset replacement is explicit. Reset controls clearly state their scope.
- Numeric inputs permit intermediate typing; bound/normalize on Enter or leaving the field. Sliders, displayed numbers and actual rendering agree.
- Preview counts describe what is actually shown. Category counts are derived from target data. Search matches the displayed repertoire and previews a matching result; clearing restores the previous selection and expansion state.
- Character categories suit the font. Label the preview style/script and show useful Unicode or sequence information. No fallback-font glyph should masquerade as native support.
- Determine feature compatibility per font. Do not transfer Bia's ss01/ss02 mutual exclusion to another family without checking its substitutions.
- Semantic headings, named controls, keyboard operation, visible focus, selected/expanded states and accessible status messages are required for added interactions. Avoid disruptive live announcements for every mouse movement.
- Honor reduced motion and provide pause for continuing animation. Never restore a saved animation as automatically running.
- Save/share is optional. If implemented, define its scope, validate state, handle blocked storage/clipboard, restore text as text, and disclose that the link includes specimen text. Do not silently truncate it.
- Licensing action is clear and uses verified destinations. Do not add trial/PDF functionality under this benchmark.

## Evidence for review

Report the concrete result, why it suits this font, how it was checked, and remaining limitations. Check small mobile, typical mobile, tablet and desktop, including breakpoint edges when the layout warrants it. Test real sequential typing, not only programmatic whole-value fills. Exercise feature conflicts, native keyboard navigation, search-empty-clear behavior, custom text preservation and save/link failures where applicable. Check target scripts and feature examples using actual font assets. Do not claim Safari/iOS or complete language validation without doing those checks.

Use Bia's `docs/bia-revision-qc.md` for examples of evidence format, not as proof that another page passed. Record only relevant checks; no universal screenshot count or forced feature checklist. Keep a concrete reviewable result on a development branch. Push, merge and deploy only within current user authorization; verify live behavior after authorized publication.
